## 今日目标
我计划实现基于练习转录生成评测报告的服务，明确 READY、INSUFFICIENT 和 FAILED 等状态的处理方式，并为正常评分、数据不足和非法评分补充单元测试。

## 实际进展
我新增了 `server/internal/coaching/evaluation/generator.go`，提交 `4d3b8aa feat(evaluation): add report generation service`。Service 接收用户、会话、报告编号、版本和问题回答组成的 `Transcript`，先检查 Repository、Scorer、身份标识、版本号和问题列表，避免无效输入进入评测流程。对于没有任何回答的练习，我直接生成 `INSUFFICIENT` 报告，不调用评分器，并保存问题列表和不可评分原因；存在回答时，再调用 `Scorer` 生成正式报告和反馈项，校验报告结构、反馈数量、评测编号及反馈有效性后，通过 D3 已完成的 Repository 事务保存，并写入完成时间。

我同时新增 `generator_test.go`，使用内存 Repository 和测试评分器覆盖三条路径：有回答时生成并保存 READY 报告；没有回答时生成 INSUFFICIENT 报告且评分器不会执行；评分结果超出范围时返回错误且不会持久化。这样把 D2 的评分约束、D3 的持久化能力和今天的生成流程连接起来。今天只有个人代码提交，没有创建或更新个人 Issue/PR。

## 遇到的问题与解决
我一开始需要决定“数据不足”应由评分器判断还是由生成 Service 判断。结合 D2 已确定的评分语义，我把零回答判断放在 Service 入口，避免无效调用外部评分器；同时保留失败报告的身份、会话和版本信息，便于后续查询和排查。另一个问题是评分器可能返回结构不完整或反馈归属错误的结果，我在写入 Repository 前增加 `FormalReport.Valid`、反馈数量和 `EvaluationID` 校验，确保错误结果不会污染历史记录。今天执行了 Go 相关单元测试，未执行 PostgreSQL 实例集成测试和 Flutter 检查，原因仍是本地没有数据库环境且本次改动只涉及 Go 评测模块。
