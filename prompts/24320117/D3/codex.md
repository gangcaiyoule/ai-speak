结论：下一步功能应做“场景列表、场景详情、角色与练习目标选择”，对应需求清单中的 R4、R5、R6。

不过要区分两件事：

1. 流程上的下一步：创建 Gitee Issue，即 R4。
2. 开发上的下一步：实现场景选择最小闭环，即 R5。

当前课程包里还没有实际业务源码，只有设计文档和任务清单，所以现在不适合直接写 Flutter 或 Go 代码。

**为什么先做这个功能**

它是后续所有练习流程的入口：

```text
场景列表
  -> 场景详情
  -> 选择角色和练习模式
  -> 进入准备页
  -> 创建练习计划
  -> 创建练习会话
  -> 交给实时练习模块
```

先做场景模块有三个好处：

- 依赖相对少，可以先验证 Flutter、Go、API、数据模型的协作方式。
- 能尽快形成用户可操作的完整链路，而不是只完成零散文件。
- 后续岗位准备、练习计划和启动流程都需要复用场景选择结果。

**更好的开发方案**

不要一次性处理整个 `coaching` 目录。建议采用“按用户闭环、纵向切片”的方式：

第一阶段：场景选择

- `GET /v1/scenes`
- `GET /v1/scenes/{scene_id}`
- 场景列表页面
- 场景详情页面
- 角色、练习模式、练习目标选择
- 必填项校验
- 加载、空数据、错误和重试状态
- 场景版本校验

第二阶段：岗位准备与练习计划

- 输入岗位名称、公司、JD、个人背景和练习重点
- 可选选择 PDF 简历
- 展示服务端返回的岗位分析草稿
- 用户编辑并确认分析结果
- 创建、查看、打开和归档练习计划

第三阶段：练习启动

- 校验场景和岗位准备上下文
- 读取或创建练习计划
- 创建练习会话
- 处理重复点击和网络重试
- 将已创建的会话交给实时练习模块

这样拆分后，每个 Issue 都能独立验收，也更容易定位问题和提交 PR。

**第一阶段的需求边界**

本阶段应该包含：

- 场景分类和场景卡片；
- 场景详情、练习目标、用户角色和 AI 角色；
- 角色选择；
- 练习模式、时长或轮次选择；
- 开始按钮状态控制；
- API 请求、JSON 解析和错误处理；
- 页面到准备页的交接；
- 对应 Flutter、Go 和接口测试。

本阶段明确不包含：

- 实时 AI 多轮问答；
- 麦克风录音；
- 语音上传、转写、播放；
- 练习中的问题展示和回答提交；
- 评分、复盘和练习报告；
- 岗位分析和 PDF 简历解析。

**建议的第一个 Issue**

标题：

```text
[功能] 完成场景列表、详情和练习目标选择
```

验收标准：

- 可以加载并展示场景列表；
- 可以打开场景详情；
- 可以选择用户角色和练习模式；
- 未完成必要配置时不能开始；
- 场景详情版本与列表版本不一致时停止启动；
- 网络失败时有明确错误和重试入口；
- 不实现实时语音功能；
- 完成实际执行过的格式化、静态检查和测试记录。

因此，最合理的动作顺序是：

```text
确认目标 Gitee 仓库和权限
  -> 创建 R4 Issue
  -> 从 main 创建功能分支
  -> 实现场景相关模型、接口和页面
  -> 完成场景选择闭环
  -> 测试并提交第一个 PR
```
