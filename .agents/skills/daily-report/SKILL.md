# 团队每日日报

为当前成员生成可复核的课程过程记录。先读取 `docs/项目实践1课程要求文档/课程过程记录提交说明.md`，再检查仓库结构、Git 历史和 Gitee 记录；只写有证据支持的个人工作。

## 路径与身份

- 日报必须保存为 `daily/<学号>/D<天数>/D<天数>.md`，例如第 1 天是 `daily/24320106/D1/D1.md`。
- 禁止使用 `daily/<学号>/D<天数>.md` 这一扁平路径，也不要把不同成员的日报写入同一目录。
- 从当前请求、Git 提交身份、已有 `daily/` 和 `prompts/` 学号目录交叉判断成员；如果出现多个冲突身份，先报告冲突，不要猜测。
- 根据已存在的 `D1`、`D2` 等目录和课程日期推断天数。已有日报时先读取并增量更新，保留用户内容和队友文件。

## 证据收集

- Git：查询当天时间范围内的提交、作者、提交信息和变更文件；必要时查看提交差异。
- Gitee：查询当天由当前成员创建或参与的 Issue、Pull Request、状态、关联关系、变更说明和 URL。企业项目 Issue 编号可能是字符串，按原样保留。
- 验证：只记录实际运行过的测试、格式化、静态检查、构建或手工验证；没有运行的检查写明“未执行”及原因。
- 团队协作：其他成员的提交、Issue 和 PR 不归入当前成员的个人进展；共同工作可写成协作事项，并明确个人实际负责部分。
- 远端状态未确认时不要声称已创建、已关联、已合并或 CI 通过。PR 和 Issue 链接必须来自 Gitee 返回的真实 URL。

## 日报结构

使用课程要求的标题；第 1 天省略“昨日遗留问题的回答”，其他天数必须回答上一日报或系统反馈中的遗留问题：

```markdown
# Dn 日报

## 昨日遗留问题的回答
## 今日目标
## 实际进展
## 遇到的问题与解决
## 明日计划
```

内容应具体到本项目的模块、接口、文档、提交和问题处理过程。优先写“发生了什么、如何定位、采取了什么方案、如何验证”，避免空泛的学习总结。

## Issue 与 PR 链接

在“实际进展”中列出当天个人记录，至少包含标题、编号、状态和 Gitee URL，例如：

```markdown
### 今日 PR

- [PR !12：实现练习会话接口](https://gitee.com/pp1-2026/24320106/pulls/12)（已合并）

### 今日 Issue

- [IKCW0Y：建立团队通用每日日报生成 Skill](https://gitee.com/pp1-2026/24320106/issues/IKCW0Y)（开放）
```

如果当天没有个人 Issue 或 PR，明确写“今天没有创建或更新个人 Issue/PR”，不要用队友链接填充。

## 写入与检查

1. 先确认目标文件和现有内容，再写入对应的 `D<天数>` 目录。
2. 不覆盖已有日报中的真实记录；合并新信息时保留原有表述和手工补充。
3. 检查 Markdown 标题、链接、学号和天数一致，并运行 `git diff --check -- <日报路径>`。
4. 完成后报告实际写入路径、发现的远端记录、未执行的验证，以及是否需要用户自行 commit/push。

本 Skill 只负责生成和检查本地日报。创建或修改 Gitee Issue、Pull Request、Milestone 时，另行遵循仓库对应的 `issue-standard` 和 `gitee-pr` Skill，并等待用户明确授权。
