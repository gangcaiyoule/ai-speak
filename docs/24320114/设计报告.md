## 一、项目概述与范围

SpeakUp 面向学生和求职者，提供模拟面试、IELTS、职场和生活场景的英语口语练习。系统将“目标理解—场景准备—多轮回答—评测反馈—同题复练—历史比较”组织成闭环。本报告只记录前两天已完成的评测与复盘契约设计；账号、场景、实时语音和数据库实现属于后续协作范围。

前两天聚焦评测数据结构、状态语义和校验；报告生成、查询、复练持久化属于后续计划。支付、数字人、音素级专业评分和自研大模型不在课程范围内。

## 二、总体架构

```text
Flutter App
  ├─ 场景/练习页面与评测报告页面
  ├─ REST Client：practice、evaluation
  └─ WebSocket voice transport
                 │ HTTPS / WebSocket
Go/Gin 模块化单体
  ├─ coaching/practice：会话、轮次、回答
  ├─ coaching/evaluation：报告、证据、反馈、复练
  ├─ identity：用户与权限
  └─ Provider adapters：ASR / LLM / TTS / Mock
                 │ pgx / SQL migrations
PostgreSQL：会话、转录、评测报告及版本数据
```

采用模块化单体是因为短周期内主要风险是契约联调和状态一致性。评测服务通过 `Scorer` 接口隔离模型输出，便于单元测试和替换 Provider。

## 三、评测与复盘设计

### 3.1 共享契约

`EvaluationReport` 将状态与正式报告分离，状态覆盖排队、运行、完成、失败和数据不足；正式报告包含场景类型、评分尺度、维度分数、证据、改进项和优先行动。每条反馈保存回答轮次、字节范围和摘录，能够回到原始转录。报告编号、用户、会话和版本均经过 UUID、长度、范围和归属校验。

### 3.2 生成流程

生成 Service 接收用户、会话、报告编号、版本和 `Transcript`。入口先检查身份、版本和问题列表；没有任何回答时生成 `INSUFFICIENT` 报告并记录不可评分原因，不调用评分器。有回答时调用 `Scorer`，验证报告结构、反馈数量、Evaluation ID 和评分范围，再通过 Repository 事务保存。任何非法结果均在持久化前返回错误。

### 3.3 后续持久化设计

后续计划按文件名排序执行迁移，并用版本表保证幂等；报告核心、证据反馈和复练版本分别落表。Repository 设计为事务写入嵌套数据，历史查询按 `actor_id` 隔离，并以 `completed_at + id` 作为稳定游标。以上属于 D2 之后的设计方向，不计入前两天已完成成果。

### 3.4 后续 HTTP 查询设计

后续评测查询层计划提供报告详情、会话查询和历史分页接口，契约位于 `api/modules/evaluation.yaml`。请求应从 Bearer 身份得到当前用户，并对 `limit`、`cursor`、`search` 做参数校验；资源不存在、参数非法和状态冲突分别返回 404、400、409。D2 阶段尚未实现这些接口。

## 四、关键数据关系

```text
practice_session 1 ── n practice_turn
practice_session 1 ── n evaluation_report
evaluation_report 1 ── n evidence / finding
evaluation_report 1 ── n repractice_version
```

报告只引用属于当前会话的回答，复练版本指向原报告和具体反馈，避免出现无法解释来源的孤立建议。删除或查询资源时由服务端再次验证用户归属。
