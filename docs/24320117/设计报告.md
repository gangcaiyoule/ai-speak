## 2. 项目背景与问题分析

英语学习者在真实练习中通常面临三个问题：第一，缺少与自身目标相匹配的语境；第二，练习前没有明确目标，导致回答内容零散；第三，练习过程和历史结果难以持续保存。SpeakUp 以岗位面试、IELTS 模考和职场沟通为主要场景，将用户选择的场景、角色、练习模式和目标转化为结构化练习计划，再生成可以逐题推进的练习会话。

我负责的模块位于整个系统的前半段。它既要让用户能够顺利开始一次练习，又要为后续实时问答和评测模块提供稳定、完整、版本明确的数据。因此，设计重点不是堆叠页面，而是保证用户意图、业务状态和数据库记录之间保持一致。

## 3. 需求与功能范围

### 3.1 用户流程

```text
登录
  -> 浏览场景列表
  -> 查看场景详情
  -> 选择角色和练习模式
  -> 填写练习目标
  -> 创建练习计划
  -> 创建并激活练习会话
  -> 查看当前问题并提交文本回答
  -> 完成练习会话
```

### 3.2 本人负责的功能

1. 场景列表、场景详情、角色和练习模式选择。
2. 场景版本和选择结果的一致性校验。
3. 练习目标填写、计划创建、查询和归档。
4. 根据场景配置生成问题快照。
5. 练习会话创建、激活、查询和完成。
6. 当前问题校验、文本回答保存和问题推进。
7. 计划、会话、问题和回答的用户隔离。

### 3.3 明确排除的内容

实时语音采集、语音转文字、文字转语音、LLM 动态对话、评分算法、评测报告和历史复盘由团队其他模块或后续版本负责。这样划分可以降低耦合，避免多人同时修改同一条业务链路。

## 4. 技术架构与选型

- **客户端**：使用 Flutter 构建跨平台页面，Controller 管理加载、成功、失败和提交状态，页面只负责展示和派发操作。
- **服务端**：使用 Go 实现模块化 HTTP 服务，采用 Handler、Service、Repository 分层。
- **数据层**：使用 PostgreSQL 保存计划、会话、问题和回答；使用 UUID 作为实体标识。
- **接口契约**：通过 REST API 和 OpenAPI 文件约定请求、响应及错误码。
- **测试方式**：Service 层通过依赖注入使用 MemoryRepository 完成快速单元测试，正式运行使用 PostgreSQL Adapter。

选择分层结构的原因是把变化隔离开来。页面交互变化时不需要改数据库逻辑，数据库实现变化时也不需要重写状态机。Handler 不直接执行 SQL，所有状态转换集中在 Service 中，便于测试和答辩时解释。

## 5. 数据模型设计

### 5.1 练习计划

计划保存 `actor_id`、`scene_id`、`scene_version`、`role_id`、`practice_option_id` 和 `objective`。其中场景版本必须保留，因为场景配置可能在后续版本中调整，历史计划仍应保持原有语义。

### 5.2 练习会话

会话引用计划，同时保存场景快照、当前问题和生命周期时间。会话创建后为 `DRAFT`，激活后进入 `ACTIVE`，所有问题完成后进入 `COMPLETED`。

### 5.3 问题与回答

问题在创建会话时从场景配置中的 `turn_blueprints` 生成，并按 `position` 保存。回答与问题一一对应，首版通过数据库约束保证同一问题不会被重复回答。保存快照可以避免场景内容变化导致历史练习内容漂移。

## 6. 状态机与错误处理

计划状态为：

```text
DRAFT -> ACTIVE -> ARCHIVED
```

会话状态为：

```text
DRAFT -> ACTIVE -> COMPLETED
```

提交回答时依次检查：会话是否属于当前用户、会话是否处于 `ACTIVE`、提交的问题是否为当前问题、回答去除首尾空格后是否为空、内容长度是否超限。检查通过后保存回答、标记问题已回答，并把当前问题推进到下一题。所有非法操作直接返回明确错误，不自动修复状态。

统一错误包括 `invalid_request`、`authentication_required`、`forbidden`、`resource_not_found`、`invalid_state_transition` 和 `internal_error`，分别对应参数错误、未登录、越权、资源不存在、非法状态和服务端异常。

立项阶段，我先阅读课程要求和仓库结构，确认自己负责的是“从场景选择到练习开始”的纵向链路。设计阶段，我把原本较宽泛的“练习功能”拆成场景、计划、会话三个层次，并画出状态转换和接口清单。实施阶段，我完成了 Flutter 场景选择和准备页面、Go 场景目录与练习服务、内存和 PostgreSQL Repository、数据库迁移、HTTP Handler、OpenAPI 契约以及对应测试。

编码过程中，我重点处理了几个容易被忽略的问题：场景详情和列表版本不一致时禁止继续；空场景列表需要单独展示；用户只能读取自己的计划和会话；归档计划不能创建新会话；重复激活、重复回答和非当前问题回答必须返回 `409`；数据库连接或迁移失败时直接暴露错误。上述决策保证了演示流程可运行，也使异常行为可以被复核。

## 10. 遇到的问题与解决方式

1. **多个模块共享会话状态**：将状态转换集中到 Service，Handler 和页面不直接修改状态。
2. **场景版本可能过期**：在客户端和服务端均保存并校验版本号，创建会话时生成快照。
3. **Flutter 环境缺失**：如实记录未执行项，优先完成 Go 链路和接口验证，不把静态代码当成移动端已验收。
