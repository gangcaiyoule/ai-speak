# 用户账户与个人中心开发方案

## 1. 目标

当前 `identity` 模块的第一阶段认证闭环已经完成并接入主线：服务端提供注册、登录、Bearer 鉴权、当前用户和退出登录接口，Flutter 客户端已接入登录注册、Token 安全存储和会话恢复。PostgreSQL 也已经具备基础 Repository 和迁移实现。本方案保留后续个人资料、设置、跨模块权限和安全加固路线，并明确区分当前实现与未来工作。

### 1.1 当前实现状态（2026-09-05）

- 已实现：注册、登录、当前用户查询、退出登录和 Token 会话恢复。
- 已实现：内存 Repository 与 PostgreSQL Repository 双实现，服务通过 `DATABASE_URL` 选择 PostgreSQL。
- 已实现：bcrypt 密码哈希、SHA-256 Token 摘要、30 天会话有效期、并发注册唯一性保护。
- 已实现：Flutter `AuthGate`、登录/注册表单、`flutter_secure_storage` Token 存储和失效 Token 清理。
- 未实现：个人资料、昵称、系统设置、修改密码、全部设备退出、账号删除和完整安全加固。
- 未完成验证：完整 Flutter Widget 测试和真实部署环境端到端联调需要单独补充记录。

核心原则：

- API 契约和领域边界先稳定，存储实现可以替换。
- 客户端不提交可信 `user_id`，用户身份始终由服务端会话解析。
- 服务端不保存明文密码和原始会话 Token。
- 每个阶段都能独立运行、测试和演示，不一次搬入参考项目的全部复杂度。
- 只负责账户、资料和权限边界，不实现练习业务或 AI 处理。

## 2. 参考项目取舍

### 2.1 第一阶段复用的设计

- `Service -> Repository` 分层，HTTP Handler 不直接访问数据。
- 注册只创建用户，登录成功后才创建会话。
- 使用随机不透明 Token，而不是把用户资料编码进 Token。
- 服务端只保存 Token 的 SHA-256 摘要。
- Bearer 鉴权成功后，将可信的 `UserID` 和 `SessionID` 写入请求上下文。
- 未知邮箱和错误密码返回相同的 `invalid_credentials`，避免泄露账号是否存在。
- Flutter 使用 `AuthController + AuthGate + SessionStore` 管理认证状态。
- 收到 `401` 时清除失效的本地会话。

### 2.2 暂不搬入的能力

- 头像上传、图片校验和对象存储。
- 账号删除及跨模块级联清理。
- 登录限流、可信代理 IP、Correlation ID 和复杂审计。
- Profile 乐观锁、幂等键和会话并发替换。
- 修改密码、全部设备退出和密码哈希自动升级。
- 与数字人、IELTS 能力、教练记忆相关的个人设置。
- 参考项目完整的部署、监控和生产安全配置。

这些能力继续沿用参考项目的方向，但分别放入后续独立 Issue，避免第一阶段范围失控。

## 3. 稳定 API 契约

### 3.1 注册

`POST /v1/auth/register`

请求：

```json
{
  "email": "learner@example.com",
  "password": "correct horse battery staple"
}
```

成功返回 `201 Created`：

```json
{
  "user": {
    "id": "<uuid>",
    "email": "learner@example.com"
  }
}
```

注册不自动创建会话。重复邮箱返回 `409 account_registration_unavailable`，非法邮箱或密码返回 `400 invalid_request`。

### 3.2 登录

`POST /v1/auth/login`

成功返回 `200 OK`，并设置 `Cache-Control: no-store`：

```json
{
  "user": {
    "id": "<uuid>",
    "email": "learner@example.com"
  },
  "session_token": "sess_<random>",
  "token_type": "Bearer",
  "expires_at": "2026-10-03T12:00:00Z"
}
```

邮箱不存在或密码错误统一返回 `401 invalid_credentials`。

### 3.3 当前用户

`GET /v1/me`

请求头为 `Authorization: Bearer <session_token>`。服务端验证 Token 摘要、会话状态和过期时间后返回当前用户。缺失、非法、已过期或已撤销的 Token 统一返回 `401 authentication_required`。

### 3.4 退出登录

`POST /v1/auth/logout`

只撤销 Bearer Token 对应的当前会话，不接受客户端提交 `user_id` 或 `session_id`。成功返回 `204 No Content`，退出后的 Token 不能继续访问 `/v1/me`。

### 3.5 错误结构

```json
{
  "error": {
    "code": "invalid_credentials",
    "message": "邮箱或密码不正确。",
    "retryable": false
  }
}
```

第一阶段统一错误结构，后续增加 Correlation ID 时无需改变成功响应。

## 4. 阶段一：最小可运行认证闭环

### 4.1 Go 服务端

> 当前状态：第一阶段已完成基础实现。下面的文件列表同时记录现有实现和后续可拆分的结构，不代表所有文件都已经独立存在。

建议调整或新增：

```text
server/internal/identity/
  model.go               用户、凭据、会话和登录结果（现有）
  ports.go               Repository 与 AuthService 接口（现有）
  errors.go              稳定领域错误（现有）
  email.go               邮箱规范化和校验（现有）
  password.go            密码校验、哈希和验证（现有）
  token.go               原始 Token 生成与摘要（现有）
  memory_repository.go   线程安全内存适配器（现有）
  postgres_repository.go PostgreSQL 适配器（现有）
  service.go             注册、登录、鉴权、当前用户和退出（现有）
  http.go                JSON、Bearer 和状态码映射（现有）
```

最小安全要求：

- 邮箱去除首尾空白并转换为小写，长度不超过 254。
- 注册密码长度为 8 至 128，登录时不重新套用新密码规则。
- 第一阶段使用 `bcrypt`，数据库阶段可增加 Argon2id 和渐进式重哈希。
- 使用 `crypto/rand` 生成至少 32 字节随机 Token，加固定 `sess_` 前缀。
- Repository 只保存 `sha256(token)`，HTTP 响应之外不记录原始 Token。
- 内存 Repository 使用 `sync.RWMutex`，保证并发注册和会话访问无数据竞争。
- 会话有效期固定 30 天，所有时间通过可注入 Clock 获取，方便测试过期行为。
- Handler 限制 JSON Body 大小、拒绝未知字段并检查 `Content-Type`。

服务启动时已经使用真实 `Service`。没有配置 `DATABASE_URL` 时使用 `MemoryRepository`，配置后使用 PostgreSQL Repository；内存模式的数据会在服务重启后丢失，必须在运行文档中明确标注这是开发模式限制。

### 4.2 Flutter 客户端

> 当前状态：已完成最小可运行认证界面和会话恢复。当前实现采用两个文件承载完整流程，下面的拆分结构属于后续可维护性重构建议。

建议调整或新增：

```text
mobile/lib/identity/
  identity_client.dart   User、LoginResult、SessionStore 和 HTTP 实现（现有）
  auth_gate.dart         会话恢复、登录/注册表单和认证入口（现有）
  auth_controller.dart   后续可从 AuthGate 拆出的状态控制器（规划）
  auth_state.dart        后续可拆出的认证状态模型（规划）
  profile_page.dart      个人中心页面（规划）
```

交互流程：

1. App 启动后读取安全存储中的 Token。
2. 没有 Token 时显示登录页。
3. 有 Token 时请求 `/v1/me`；成功进入现有练习页，`401` 时删除 Token 并显示登录页。
4. 注册成功后切回登录页并预填邮箱，不自动假装已登录。
5. 登录成功后先保存 Token，再进入练习页。
6. 退出时先请求服务端撤销会话，再清除本地 Token；网络失败也允许用户清除本地会话。

页面采用克制的单列表单结构：邮箱、密码、主操作按钮和登录/注册切换入口。必须包含加载禁用、字段错误、服务错误、密码显隐、键盘提交和滚动适配，不增加营销 Hero、插画或装饰性卡片。

### 4.3 阶段一验收

- 注册新用户成功，重复注册失败。
- 新用户可以登录并进入现有 `/practice` 页面。
- App 重启后可以恢复仍有效的会话。
- 退出后原 Token 请求 `/v1/me` 返回 `401`。
- 服务端内存中不存在明文密码和原始 Token。
- 并发注册同一邮箱最多成功一次。
- Go 单元测试、HTTP 测试、`go vet` 和构建通过。
- Flutter Controller、Client、SessionStore 和 Widget 测试通过；无法执行时如实记录环境限制。

## 5. 阶段二：PostgreSQL 持久化

阶段二保持 Service、Handler 和 Flutter 不变，只替换 Repository。

### 5.1 当前数据库结构

```text
users
  id text primary key
  canonical_email text unique not null
  status text not null default 'active'
  created_at timestamptz not null
  updated_at timestamptz not null

credentials
  user_id text primary key references users(id) on delete cascade
  password_hash text not null
  updated_at timestamptz not null

auth_sessions
  id uuid primary key
  user_id text references users(id) on delete cascade
  token_digest text unique not null
  created_at timestamptz not null
  expires_at timestamptz not null
  revoked_at timestamptz null
  revocation_reason text null
```

当前实现位于 `server/migrations/0005_identity_auth.sql`，使用 `database/sql` 和 `github.com/lib/pq` 完成 PostgreSQL 访问。已实现用户、凭据和认证会话三张表，以及唯一邮箱、Token 摘要、会话过期和撤销相关约束。事务、连接池配置和部署级数据库运维仍属于后续完善项；如果未来评估迁移到 `pgx/pgxpool`，应另开技术改造 Issue，不应在本方案中当作当前事实。

### 5.2 阶段二后续完善验收

- 服务重启后用户仍可登录。
- 数据库中只有密码哈希和 Token 摘要。
- 用户创建与凭据创建在同一事务中。
- 过期或撤销会话无法鉴权。
- PostgreSQL 集成测试覆盖唯一邮箱、事务回滚和会话隔离。

## 6. 阶段三：个人资料与最小系统设置

### 6.1 个人资料

先只支持昵称：

- `GET /v1/me/profile`
- `PATCH /v1/me/profile`
- Flutter 个人中心展示邮箱、昵称和退出登录。
- 编辑昵称支持 1 至 40 个字符、加载状态和错误反馈。

可参考 `XE3-ESL` 的 `profile_version` 乐观锁，但第一版可以先用单用户最后写入生效；出现多设备编辑需求时再增加版本字段和 `409 profile_version_conflict`。

### 6.2 系统设置

最小设置建议只选确实会被产品使用的字段：

- 界面语言：`zh-CN` / `en-US`
- 自动播放 AI 语音：开/关
- 练习提醒：开/关

设置保存到独立 `user_settings` 表，通过 `GET/PATCH /v1/me/settings` 管理。主题若完全由设备系统决定，可只保存在本地，不必写入服务端。

## 7. 阶段四：权限隔离和跨模块接入

身份模块向其他模块提供统一鉴权中间件。练习、简历、音频、转录和报告接口不得接受客户端提交的可信用户归属，查询必须同时包含资源 ID 和当前 Actor 的用户 ID。

必须增加双用户测试：

- 用户 A 无法读取、修改或删除用户 B 的资源。
- 猜测另一个资源 ID 不会绕过权限校验。
- 错误响应不泄露其他用户资源是否存在。
- WebSocket 握手同样校验会话，不只保护 REST。

## 8. 阶段五：逐步接近 XE3-ESL

按风险和演示价值排序：

1. 登录限流和安全日志脱敏。
2. 修改密码并撤销全部旧会话。
3. 账号删除状态及跨模块清理流程。
4. 头像上传、格式/尺寸限制和私有对象存储。
5. Profile 乐观锁和头像更新幂等键。
6. Argon2id、参数版本和登录时自动重哈希。
7. 可信代理来源 IP、Correlation ID、审计和监控指标。

是否迁移到 Gin 应作为独立的全仓库技术决策。当前其他模块使用 `net/http`，身份模块不应单独引入另一套路由框架，否则会增加启动组合和中间件复用成本。
