# 《项目实践1》课程思政报告

**课程名称：** 项目实践1（Project Practice 1）  
**项目名称：** SpeakUp：基于 Flutter 与 Go 的 AI 英语口语陪练系统  
**学号：** 24320106  
**姓名：** 张思成  
**实践时间：** 2026 年 9 月 1 日—9 月 6 日

## 一、实践背景与价值认识

本次项目实践围绕“如何让英语学习者获得低门槛、可反复、可追踪的口语训练”展开。团队选择 AI 英语口语陪练作为题目，是因为身边同学在求职、升学和国际交流中普遍有开口机会少、反馈不及时、练习难以持续等问题。SpeakUp 不是单纯把聊天机器人接到页面上，而是尝试把目标理解、场景准备、连续问答、证据化反馈和同题复练串成一个学习闭环。这个选题使我认识到，计算机专业学习的价值不仅是把程序运行起来，还在于用可靠的工程方案回应真实需求，承担技术对学习效率、隐私和公平性的影响。

课程大纲提出要把个人、集体和国家发展联系起来，并在实践中落实爱国、诚信、敬业、友善。AI 和英语技术长期由国外公司占据较大影响力，项目实践让我看到差距，也让我更具体地理解“科技报国”不是口号：一方面要正视模型、语音链路、跨端工程等方面的不足，另一方面要通过学习基础原理、建立可替换的 Provider 接口、沉淀接口契约和测试，把系统做得可解释、可维护、可持续改进。只有愿意从身份认证、错误处理、数据迁移等小事做起，才可能形成以后承担更大工程的能力。

## 二、我在项目中的实际投入

我是项目组组长，负责用户账户与个人中心方向，同时承担需求基线、进度协调、代码集成和交付材料整理。我的工作不是代替队友完成所有模块，而是把团队目标拆成可以验收的 Issue，明确模块边界和接口约束，并在联调时帮助解决跨模块问题。

具体贡献包括：

1. **建立工程基线和协作规则。** 我将原有 GitHub 协作约定切换为课程要求的 Gitee 主仓库，补充 Issue、Milestone、分支和 Pull Request 规则，建立 `todos.md` 需求清单，并推动 Go/Flutter CI 检查。
2. **完成身份认证服务端纵向切片。** 我实现了 Go/Gin 注册、登录、退出和会话认证 API，先用内存仓储验证业务边界，再增加 PostgreSQL 凭据与会话持久化、Token 摘要存储和用户隔离检查；同时补充迁移和服务端测试。
3. **完成客户端会话恢复。** 我在 Flutter 侧接入安全存储、认证表单和登录后的会话恢复入口；针对应用重启后存在 DRAFT/ACTIVE 练习会话的情况，增加可恢复会话查询和继续练习路径，失败时保留重试或回到准备页的选择。
4. **补齐文本回答与边界约束。** 在语音环境不稳定时，我参与实现文本回答提交路径，并在服务端约束“回答不能为空、只能提交当前轮次、已完成轮次不能重复提交”等不变量。
5. **参与文档、测试和交付。** 我记录 D1—D5 日报及提示词材料，维护账户开发方案和需求清单，执行 `cd server && go test ./...`、`go vet ./...`、`go build ./...`，如实记录本机没有 Flutter/Dart SDK、因此没有执行客户端命令的限制。

上述工作可以在仓库提交、日报、Issue 和 PR 中逐项核验，例如 PR #22、#24、#27、#34、#38、#39、#40、#41，以及 Issue `IKDABZ`、`IKDAR5`、`IKDB8J`、`IKDICY`、`IKDII9` 等。提交材料只引用实际完成的工作，不把 AI 生成的内容冒充为我的独立思考。

## 三、课程思政主题在实践中的体现

### 1. 个人、团队、社会和国家的统一

我把自己的模块看作团队整体的一部分。身份服务如果只考虑“我这段代码能跑”，而不考虑场景、练习和客户端如何使用，就会造成队友等待和集成返工。因此我先和队友约定 REST/JSON 字段、错误语义、用户资源归属和状态转换，再实现代码；发现客户端 SDK 缺失时，也及时在日报中说明，让团队调整验证策略。项目最终服务的是学习者，用户的简历、语音和回答包含个人信息，设计“只允许访问自己的资源”、限制文件类型与大小、服务端保存密钥等措施，是对社会责任和工程伦理的具体落实。

### 2. 爱国、诚信、敬业与友善

在技术选型中，我没有因为“国外产品看起来成熟”就简单照搬，而是比较现有方案，保留可替换的模型适配层，努力理解系统的关键控制点。对于第三方 AI 不可用、Docker 镜像受代理影响、Flutter 环境缺失等问题，我都记录真实原因和替代方案；对于没有执行的测试，明确写“未执行”，没有用想象中的结果填充报告。每天同步完成项、阻塞项和下一步，及时 review 队友 PR，既是敬业，也是对队友劳动的尊重。出现接口分歧时先讨论事实和验收标准，不把问题归咎于个人，尽量用文档和测试消除误解。

### 3. 精益求精和工匠精神

认证功能看似简单，但密码不能明文保存、Token 不能直接落库、退出后旧会话应失效、不同用户不能读取彼此数据，这些细节决定系统是否可信。我在实现中采用密码哈希和 Token 摘要，设计可幂等的数据库迁移，增加空值、重复提交、过期会话和未授权访问测试。练习恢复功能也经历了“前端有入口但服务端状态不完整”的返工，我将状态机和恢复条件写清楚，再补上 204、重试和已完成会话不恢复等边界。这些小范围的反复验证，让我体会到工匠精神不是追求表面复杂，而是对每个可观察行为负责。

### 4. 独立思考与诚信使用 AI

我使用 Codex 等 AI coding agent 辅助检索仓库、生成测试初稿、解释编译错误和整理 Markdown，但关键决策由我提出并核对：哪些需求进入 P0、哪些风险必须降级、认证数据如何隔离、测试命令是否真的执行。对 AI 给出的代码，我逐段检查接口边界、错误处理、并发行为和迁移顺序；对不符合仓库规则的内容进行删改。提示词记录保存在 `prompts/24320106/`，日报保存在 `daily/24320106/`，这使 AI 参与过程可追溯，也提醒我不能把“生成过”当成“理解过”。

## 四、问题、反思与改进

本次实践也暴露出三点不足。第一，短学期时间紧，个人模块投入较多，需求清单和报告整理一度滞后，说明我对文档债务的估计不足。第二，本机缺少 Flutter/Dart SDK，客户端测试主要依赖代码检查和 CI，降低了本地端到端验证的充分性。第三，AI 反馈质量、语音延迟和真实用户学习效果还没有足够长期数据，当前结论只能说明工程闭环可行，不能夸大为教学效果已经被证明。

后续我会提前准备统一开发镜像或 Codespaces，建立客户端、服务端和数据库的一键验证脚本；为 AI 输出增加更多可解释的评测样例和人工抽检；在保护隐私的前提下收集匿名指标，比较复练前后的表达变化；继续学习语音处理、分布式系统和软件工程管理，把一次课程实践转化为长期能力。更重要的是，在未来团队项目中继续坚持事实记录、主动沟通、互相帮助和对社会影响负责。

## 五、结语

这次项目让我认识到，计算机工程师的职业道德落实在每一次提交、每一条错误信息、每一个权限判断和每一次诚实的测试记录中。SpeakUp 目前仍是课程项目，但它让我把个人成长、团队交付和用户价值联系起来，也让我更坚定地把专业学习用于解决真实问题、提升自主工程能力，并以可靠、诚信和持续学习的态度参与数字化建设。
