## 一、项目概述

SpeakUp 面向缺少真实英语表达环境的学生和求职者，提供模拟面试、IELTS、职场与生活场景练习。系统将“目标理解—场景准备—多轮回答—反馈分析—同题复练—历史比较”组织为闭环。团队采用 Flutter 跨端客户端、Go/Gin 模块化单体后端、PostgreSQL 和 Docker；ASR、LLM、TTS 通过 Provider/Adapter 接入，第三方服务不可用时使用 Mock 保证业务链路可演示。

本报告记录最终实现中可核验的设计与个人负责部分，不把立项阶段的设想误写成已完成能力。课程期间已完成的重点增量是认证闭环、会话持久化、文本回答、未完成练习恢复、接口契约和 CI/过程材料；完整语音和 Flutter 真机验证仍受环境与时间限制。

## 二、需求与范围

### 2.1 用户需求

- 注册、登录、退出并在重启 App 后恢复会话；
- 选择练习场景，输入岗位/目标和个人背景；
- 通过语音或文本回答 AI 的连续提问；
- 查看回答原文、结构化反馈、优化表达和历史版本；
- 对同一问题复练，比较前后变化；
- 个人简历、音频、转录和报告按用户隔离并可删除。

### 2.2 版本范围

P0 保证身份认证、场景/练习准备、练习会话状态、回答提交和报告查询的闭环；P1 包括历史、复练、更多语音 Provider 和运维统计。支付、数字人、音素级专业评分、自研大模型不在本次课程范围内。将范围拆成 Issue 和 Milestone，避免在验收阶段继续扩大需求。

## 三、总体架构

```text
Flutter App
  ├─ AuthGate / secure storage / practice UI
  ├─ REST client：identity、scene、practice、evaluation
  └─ WebSocket voice transport（语音链路）
                 │ HTTPS / WebSocket
Go/Gin 模块化单体
  ├─ identity：用户、凭据、会话、权限
  ├─ coaching/scene：场景与练习计划
  ├─ coaching/practice：会话、轮次、回答状态
  ├─ coaching/evaluation：报告、证据、反馈、复练
  ├─ agent：目标理解与文本生成接口
  └─ provider adapters：ASR / LLM / TTS / ISE / Mock
        │ pgx / SQL migrations
PostgreSQL ── 结构化业务数据
对象存储 ─── 简历和音频（私有归属）
```

采用模块化单体而不是微服务，是因为项目周期短，主要风险是接口联调和状态一致性，而不是独立扩缩容。各领域模块持有自己的业务状态，外部模型通过接口隔离，便于替换供应商和编写 Mock。

## 四、关键技术设计

### 4.1 身份认证与数据安全

注册时校验邮箱和密码规则，密码使用哈希保存；登录成功后生成随机 Token，数据库只保存 Token 摘要及过期时间。请求通过认证中间件解析当前用户，Repository 查询始终带 `user_id` 条件；退出操作撤销会话。简历、音频和报告的访问不能仅依赖客户端传参，服务端必须再次校验资源归属。API Key 只通过服务端环境变量注入，不写入仓库。

### 4.2 练习会话状态机

会话至少包含 `DRAFT`、`ACTIVE`、`COMPLETED` 等状态。准备页创建 DRAFT，激活后进入 ACTIVE，每轮回答成功提交后推进当前题，达到轮数或完成条件后进入 COMPLETED。服务端提供最近可恢复会话查询：只返回当前用户最近更新的 DRAFT/ACTIVE；无记录返回 204，已完成会话不恢复。客户端登录后先请求该接口，ACTIVE 直接恢复当前题，DRAFT 展示继续入口；请求失败显示重试或重新准备，而不是静默丢失进度。

### 4.3 回答提交不变量

回答接口同时支持文本和语音转录结果。服务端检查会话归属、轮次归属、回答非空、当前轮次未完成以及会话状态可写，成功后持久化回答和元数据。重复请求不能生成多个已完成回答；非法顺序返回明确错误。这样即使网络重试或前端状态过期，也不会破坏报告生成的前置条件。

### 4.4 数据库迁移

迁移文件按文件名排序执行，版本表记录已执行版本，重复执行会跳过。`0002`—`0004` 分别覆盖评测报告核心、证据/逐句反馈、复练及版本数据；`0005`—`0006` 覆盖身份认证和练习计划。迁移逻辑在空库升级和重复执行场景下测试，保证开发环境与 CI 的结构一致。

### 4.5 客户端分层与跨端约束

Flutter 采用页面—Controller—Client—HTTP 分层，认证状态由 AuthGate 管理，安全存储只负责凭据生命周期。语音层抽象采集、切帧、传输和播放；iOS 使用激活后的采样率，Oboe 无硬件时间戳时使用单调时钟。由于本机未安装 Flutter/Dart SDK，本阶段未声称执行 `flutter analyze` 或 `flutter test`，相关检查保留给 CI/具备 SDK 的环境。

## 八、运行与交付说明

服务端依赖 Go 和 PostgreSQL，可在 `server` 目录运行测试和构建；数据库通过迁移程序初始化。生产部署建议使用 Docker Compose、Nginx HTTPS/WebSocket 反向代理、PostgreSQL 和私有对象存储，模型密钥由环境变量提供。客户端需要 Flutter 3.44.6/Dart 3.12 或兼容版本，实际设备需授予麦克风权限。详细接口契约位于 `api/modules/`，代码和测试分别位于 `server/`、`mobile/`。

## 九、成果、局限与后续计划

本项目完成了从账号、练习准备、回答提交到评测/复练的可扩展骨架，并通过模块化、迁移、测试和 PR 记录保留工程证据。当前局限是客户端本地验证不足、真实 AI/语音服务受网络和密钥影响、场景数量有限、缺少长期用户数据。后续优先补齐 Flutter 一键环境和端到端测试，增加 Provider 超时/重试和可观测性，建立匿名评测集，比较复练版本的结构完整度、可理解度和表达自然度，在隐私保护前提下持续改进。

## 十、结论

SpeakUp 的设计重点不是堆叠模型能力，而是用清晰的状态、权限、接口和反馈结构把 AI 能力纳入可验证的软件工程流程。通过本次实践，我完成了个人负责的认证与会话增量，也理解了一个复杂工程问题必须经过需求约束、协作分工、实现、测试、记录和答辩才能真正交付。
