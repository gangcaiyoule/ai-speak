# SpeakUp：基于 Flutter 与 Go 的 AI 英语口语陪练系统

## 一、题目

**SpeakUp：基于 Flutter 与 Go 的 AI 英语口语陪练系统**

项目类型：Flutter 跨端客户端 + Go Web 后端的全栈应用

课程周期：2026 年 9 月 1 日至 9 月 6 日集中开发，9 月 7 日完成期末报告

课程工作量：每人约 64 小时（课内 32 学时、课外约 32 小时），四人合计约 256 人时

## 二、摘要

本项目面向缺少真实英语表达环境的学习者，解决练习场景单一、反馈笼统和难以复练的问题。系统提供 AI 语音对话、模拟面试、IELTS 与生活职场场景、即时反馈和历史复盘。项目基于任务驱动学习和证据化反馈，采用 Flutter、Go/Gin、PostgreSQL、REST/WebSocket/WebRTC、ASR/LLM/TTS 及 Docker，在现有开源代码基础上完成可运行、可演示的跨端应用与后端增量版本。

## 三、调研与同类产品分析

### 3.1 调研对象

项目组已对国内外 AI 英语口语和面试训练产品进行了网络调研，重点参考：

1. **Speak**：以 AI 实时口语对话和即时纠错为核心，优势是低压力、高频开口和实时交互；不足是面向通用英语学习，技术面试上下文和结构化复练能力不足。
2. **ELSA Speak**：以发音评测、跟读和可视化反馈见长，适合发音矫正；不足是以单句或跟读为主，难以训练技术面试中的临场组织、追问和项目表达。
3. **Duolingo Max**：具有成熟的课程体系、角色对话和 AI 互动能力，优势是内容组织和用户留存机制；不足是面向大众语言学习，不能深入结合岗位描述、简历经历和面试目标。
4. **Talkpal / Praktika / Hi Echo**：强调角色扮演、实时语音或沉浸式对话，能够提升互动感；不足是专业面试语境、回答证据分析和同题复练闭环仍不够聚焦。
5. **传统真人外教或面试辅导**：反馈通常较真实，但价格高、时间难约，难以支持高频和版本化复练。

### 3.2 功能和技术对比

| 产品或方案 | 主要交互 | 语音能力 | 场景专业度 | 反馈方式 | 主要不足 |
|---|---|---|---|---|---|
| Speak | 实时 AI 对话 | 支持实时语音、部分场景可打断 | 通用英语 | 即时纠错、学习反馈 | 缺少技术面试岗位上下文 |
| ELSA Speak | 跟读、单句练习 | 发音评测较强 | 发音训练 | 音素/单词级反馈 | 临场对话和追问较弱 |
| Duolingo Max | 课程+角色对话 | AI 语音交互 | 通用英语 | 课程进度和对话反馈 | 不针对简历和岗位经历 |
| Talkpal/Praktika | 角色扮演、自由对话 | 实时语音、角色化 | 泛场景 | 对话后建议 | 反馈不一定绑定回答证据 |
| 真人陪练 | 真人一对一 | 自然语音 | 可定制 | 人工点评 | 成本高、难高频复练 |
| **SpeakUp** | 受控模拟面试+语音回答 | WebSocket 语音链路，ASR/LLM/TTS | **英文技术岗位面试** | **原话证据、结构分析、优化表达、同题复练** | 首期场景较窄，模型效果需持续验证 |

### 3.3 调研结论

市场已经验证了 AI 口语对话、语音反馈和角色练习的需求，但现有产品普遍把“该练什么、怎样准备、如何实战、看完报告后怎样继续”的判断留给用户。本项目的差异化不是单纯增加聊天入口，而是由主 Agent 理解学习目标，组织面试、IELTS、职场或生活场景训练，再把反馈落实到下一次练习。

## 四、需求列表

### 4.1 核心用户故事

1. 作为英语学习者，我希望用文字或语音说明练习目标，从而快速进入合适的训练场景。
2. 作为准备外企面试的学生，我希望输入岗位描述和个人经历，从而练习与目标岗位相关的问题。
3. 作为 IELTS 考生，我希望选择 Part 1、Part 2、Part 3 或完整模考，从而熟悉真实考试节奏。
4. 作为口语表达不稳定的用户，我希望通过语音回答并接受连续追问，从而模拟真实交流中的临场表达。
5. 作为完成练习的用户，我希望看到评分证据、问题定位和更自然的表达，从而知道下一次具体应该改什么。
6. 作为需要反复训练的用户，我希望对同一个问题重新回答并保留历史版本，从而比较自己的改进过程。
7. 作为用户，我希望只能访问自己的简历、音频、回答和报告，从而保护个人隐私。
8. 作为项目管理员，我希望看到服务健康状态、错误日志和基础使用统计，从而及时发现系统问题。

### 4.2 功能需求

#### P0：核心闭环

- 用户注册、登录、退出登录；
- 由主 Agent 识别用户当前的学习、练习或交流目标；
- 选择模拟面试、IELTS、职场英语或生活旅行等场景；
- 在面试模式中编辑目标岗位、岗位描述和练习重点，并可选上传 PDF 简历；
- AI 以面试官、考官或场景角色身份提出英文问题；
- Flutter 客户端录音并通过 WebSocket/WebRTC 上传语音；
- ASR 将语音转写为文本；
- LLM 根据场景目标、用户背景和上一轮回答生成受控追问；
- TTS 播放面试官语音；
- 完成约 3—4 轮问答；
- 生成结构化反馈，包括回答结构、表达问题、可理解度、原句和优化表达；
- 从反馈进入同题复练、下一场景或主 Agent 对话。

#### P1：持续学习与管理

- 查看练习历史；
- 按表达、语法、词汇和明显影响理解的问题整理错题；
- 对回答进行版本对比；
- 删除个人简历、音频、转录和练习记录；
- 管理个人基础资料和系统设置；
- 管理员查看健康检查和基础使用指标。

#### 暂不实现

- 会员支付、订单和优惠券；
- 职位搜索、自动投递和求职社区；
- 数字人视频面试官；
- 音素级专业发音评分；
- 自研 ASR、TTS 或大语言模型；
- 无约束地实时生成无限问题；
- 多名面试官同时在线视频面试。

### 4.3 非功能需求

- 可用性：核心流程在演示环境中可完整运行，错误时提供明确状态和重试入口；
- 性能：普通 WebSocket 消息应在可接受时间内返回，记录语音识别、模型生成和语音播放延迟；
- 安全性：用户业务数据按用户 ID 隔离，API 密钥只保存在服务端，上传文件限制大小和类型；
- 可维护性：ASR、LLM、TTS 使用 Provider 接口隔离，便于替换供应商；
- 可测试性：核心领域规则、接口校验、数据访问和关键前端流程具备自动化测试。

## 五、技术方案

### 5.1 系统架构

采用“Flutter 跨端客户端 + Go Web 后端 + 模块化单体 + Port/Adapter”的架构：

```text
Flutter Android/iOS 客户端
       │ REST/OpenAPI：账户、目标、场景、历史、报告
       │ WebSocket：实时语音、转录、Agent 与练习事件
       ▼
Go + Gin 后端
       ├── Identity：用户和权限
       ├── Agent：目标理解、工具调用和训练编排
       ├── Preparation：岗位、简历、IELTS 与练习计划
       ├── Practice：场景、Session、Turn 和实时会话
       ├── Evaluation：转录、反馈和复练
       ├── Provider：ASR / LLM / TTS / ISE / OCR 适配
       └── Admin/Observability：健康检查、日志和指标
       │
       ├── PostgreSQL：业务数据、状态、反馈和历史版本
       ├── 对象/本地文件存储：PDF、音频和报告附件
       └── 第三方 AI 服务：ASR、LLM、TTS
```

系统采用按业务能力拆分的模块化单体，不在一周课程中额外拆分微服务。业务状态由对应领域模块唯一持有，供应商能力通过 Port/Adapter 接入。一周增量开发的主要风险是环境、模块理解和集成，而不是独立扩缩容能力不足。

### 5.2 开发平台、语言、框架和库

| 层次 | 采用方案 |
|---|---|
| 客户端 | Flutter 3.44.6、Dart 3.12，面向 Android/iOS |
| 客户端库 | record、audioplayers、flutter_tts、file_picker、image_picker、flutter_secure_storage 等 |
| 后端 | Go 1.26.6、Gin 1.11、gorilla/websocket |
| 接口 | REST/JSON、OpenAPI、WebSocket Schema、JSON Schema |
| 数据库 | PostgreSQL 18 |
| 数据访问 | pgx、GORM、golang-migrate 与 SQL 迁移脚本 |
| AI 与语音 | 千问文本/ASR/TTS、讯飞 ISE 等，通过 Provider Adapter 接入 |
| 文件处理 | PDF 文本提取、PaddleOCR、OSS/S3 兼容对象存储 |
| 测试 | flutter test、integration_test、Go test、PostgreSQL 集成测试、契约测试 |
| 构建部署 | Make、Docker、Docker Compose、Nginx、Linux；支持 Android APK 分发 |
| 项目管理 | GitHub Issues、Milestones、Pull Requests、Projects、Actions |

### 5.3 开发环境与运行环境

开发环境：Flutter 3.44.6、Dart 3.12、Go 1.26.6、Node.js 22.16 或更高版本、Git、Docker 与 Docker Compose，以及 Android 真机或 iOS Simulator。主要使用 VS Code、Android Studio 或 JetBrains IDE。

运行环境：Flutter App 运行于 Android 真机或 iOS；本地开发命令启动 PostgreSQL、执行迁移并运行 Go 后端。服务端可通过 Docker Compose 部署到 Linux，Nginx 提供 HTTPS 和 WebSocket 反向代理，PostgreSQL 保存结构化数据，音频和简历进入私有文件/对象存储，AI API 密钥通过环境变量注入。

### 5.4 数据模型概述

核心实体包括：

- `User`：用户账户；
- `Resume`：用户简历及文件元数据；
- `InterviewPlan`：岗位、简历和练习重点的历史快照；
- `InterviewSession`：一次完整面试或专项练习；
- `Turn`：问题、回答、转录和状态；
- `TurnAnalysis`：结构化分析、语音指标和算法版本；
- `FeedbackItem`：具体问题、原句、优化表达和改进建议；
- `RetryAttempt`：同题复练的新回答版本；
- `AudioAsset`：音频文件的归属、格式、大小和时长元数据。

历史面试使用不可变快照，用户后续修改或删除简历不改变已经完成的面试记录。

主要技术风险及应对：

| 风险 | 应对措施 |
|---|---|
| 模型响应慢或不稳定 | 记录延迟；限制上下文；使用 Mock；Provider 可替换 |
| 语音格式兼容问题 | 统一 PCM/WAV 规范；在客户端和服务端记录音频元数据 |
| AI 生成内容不受控 | 使用岗位、经历和当前目标的结构化上下文；后端校验 JSON Schema |
| WebSocket 断线 | 心跳、连接状态机、当前回答重试和明确错误状态 |
| 范围过大导致延期 | P0/P1 分级；支付、数字人、音素评分等列入不做清单 |
| 隐私和密钥泄露 | API Key 只在服务端；用户资源按归属校验；限制文件大小和类型 |

### 9.2 团队可行性

四名成员按客户端、后端数据、AI 语音、产品测试交付划分职责，且每人都有独立可演示成果。为保证在 6 天内高效协作，采取以下措施：

1. 使用 GitHub Issues 管理需求、缺陷和调研任务，每个 Issue 写明背景、目标、验收标准和负责人；
2. 使用 Milestone 管理版本节奏，按 M1、M2、M3 进行检查，不把所有功能拖到最后一周；
3. 使用 Git 分支和 Pull Request 开发，禁止直接把未经说明的实验代码合并到主分支；
4. 每个 PR 关联 Issue，并至少由一名其他成员进行代码或文档 Review；
5. 前后端、数据库和 AI 模块先约定接口契约，再并行开发；
6. 每天收工前同步“完成内容、下一步、阻塞问题”，第 4 天单独准备中期报告和上机演示；
7. 所有关键决策记录在 Markdown 文档中，包括技术选型、范围变更、模型更换和已知限制；
8. 代码提交遵循统一格式，重要功能同时提交测试、运行说明或截图；
9. 对成员任务设置替代方案，任何单点阻塞超过一个工作日必须在群内提出，由组长重新分配或降低范围；
10. 第 5 天冻结新增需求，第 6 天只处理缺陷、集成、演示、文档和答辩材料，避免验收阶段继续扩大需求。
